[앞 글](/posts/naver-search-advisor-site-audit/)에서 네이버 서치어드바이저 웹마스터 가이드와 Google Search Central 을 읽고 [BestOW UI](https://bestow-ui.com/) 문서 사이트를 고쳤습니다. 이 블로그도 같은 기준으로 손봐야 했습니다. Search Console 을 보니 28일 동안 노출이 60번뿐이었고, 그마저 영어 낱말 검색어였습니다.

가이드를 다 읽고 나니 문제가 하나 남았습니다. 다음에 새 쪽을 만들거나 글을 쓸 때마다 AI 코딩 도구에게 이 기준을 다시 설명해야 합니다. 그래서 기준을 **Claude Code 스킬**로 묶었습니다. 저장소는 [Dev-BestOW/korean-seo-skill](https://github.com/Dev-BestOW/korean-seo-skill)(MIT)입니다. 이 글은 스킬을 만든 방법과, 스킬이 정말 결과를 바꾸는지 잰 방법을 정리합니다.

## 스킬이 무엇인가

Claude Code 스킬은 `SKILL.md` 파일 하나와 필요한 참고 파일·스크립트를 담은 폴더입니다. 맨 위 `description` 을 보고 모델이 "지금 이 스킬이 필요한가" 를 판단해, 필요할 때만 본문을 읽습니다. korean-seo 는 웹 페이지 메타·사이트맵·RSS·블로그 제목을 다룰 때 켜지게 적었습니다.

```text
skills/korean-seo/
  SKILL.md              핵심 점검표(126줄) — 항상 읽는 부분
  reference.md          네이버 가이드 54개 문서 요약과 원문 주소
  google-reference.md   구글 핵심 44쪽 요약과 원문 주소
  scripts/check-site.py 배포된 사이트 검사(Python 표준 라이브러리만)
  scripts/check-meta.mjs 마크다운 글 제목·설명 검사(Node 표준 라이브러리만)
```

문서별 요약은 따로 두었습니다. 본문이 길면 스킬이 켜질 때마다 그만큼 읽어야 해서, `SKILL.md` 에는 판단에 바로 쓰는 기준만 남겼습니다.

## 점검표만으로는 부족했던 것

처음에는 기준을 나열하면 될 줄 알았습니다. 하지만 모델이 기준을 알아도 어기는 경우가 있었습니다.

**글자 수를 눈으로 셉니다.** 한글 제목의 글자 수를 모델도 사람도 자주 틀립니다. 그래서 메타를 내놓을 때는 표를 함께 내고, 글자 수는 도구로 세라고 적었습니다.

```markdown
제목·설명·head 태그를 내놓을 때마다 아래 표를 함께 낸다. **글자 수는 눈으로 세지 말고 도구로 센다**
(예: `python3 -c "print(len('제목'))"`). 사람도 모델도 한글 글자 수를 자주 틀린다.
```

**요청을 그대로 따릅니다.** "키워드를 다 넣어서 제목을 다시 바꿔 줘" 라고 하면 모델은 키워드를 늘어놓은 긴 제목을 만듭니다. 네이버 가이드는 키워드 반복과 검색만을 위한 잦은 제목 변경을 불이익 대상으로 적고 있습니다. 그래서 이런 요청에는 기준 안의 제목 하나와, 나머지 키워드를 설명·소제목·본문에 한 번씩 둘 곳을 제안하게 했습니다. 모델이 할 법한 핑계와 사실을 나란히 적은 표도 넣었습니다(일부).

| 이런 생각이 들면                              | 사실                                                                                     |
| --------------------------------------------- | ---------------------------------------------------------------------------------------- |
| "사용자가 키워드를 다 넣으라고 했으니 넣는다" | 반복·나열은 네이버가 명시한 불이익 사유. 기준 안의 안 + 나머지 키워드를 둘 곳을 제안한다 |
| "Breadcrumb 첫 항목은 원래 '홈'이다"          | 구글은 괜찮지만 네이버 가이드는 일반 낱말 대신 쪽을 설명하는 이름을 요구한다             |

## 셀 수 있는 것은 스크립트로

숫자로 확인할 수 있는 기준은 모델의 판단에 맡기지 않고 스크립트로 검사합니다. 둘 다 설치할 것이 없게 표준 라이브러리만 썼습니다.

- **`check-site.py`**: 배포된 사이트를 네이버 검색로봇 이름(`Yeti`)으로 요청합니다. robots.txt·301·404·사이트맵을 확인하고, 사이트맵의 모든 쪽에서 title·description·canonical·OG·파비콘·h1·alt·이동 경로를 봅니다. og:image 는 파일을 받아 크기(150×150 초과)·용량(5,000 byte 이상)·비율(3:1 이내)을 잽니다. 같은 쪽을 일반 브라우저 이름으로도 받아 비교해, 로봇에게만 다른 내용을 주는 쪽(클로킹으로 보일 수 있음)을 찾습니다.
- **`check-meta.mjs`**: 마크다운 글의 프론트매터 title·description 이 40자·80자를 넘으면 실패(exit 1)하고, 같은 낱말 반복은 경고합니다.

`check-meta.mjs` 는 이 블로그의 `pnpm check` 에 넣었습니다. 처음 돌리자마자 같은 날 오전에 바꾼 글 제목에서 "입력" 이 두 번 나온 것을 찾았습니다. 낱말 반복 검사는 조사까지 붙여 세는 단순한 방식이라 "미디어 쿼리는 … 컨테이너 쿼리는" 같은 비교 문장도 잡습니다. 그래서 실패가 아니라 경고로 두고, 사람이 읽고 판단합니다.

## 스킬이 결과를 바꾸는지 재기

스킬을 만들고 "좋아졌다" 고 느끼는 것과 실제로 좋아진 것은 다릅니다. 그래서 같은 요청을 **스킬 없이·있이** 시켜 답을 비교하는 평가를 만들었습니다.

### 요청과 검사

요청 6개를 `evals/evals.json` 에 적고, 요청마다 답에서 확인할 검사를 붙였습니다. 하나를 예로 들면 이렇습니다(실제 파일).

```json
{
  "id": "keyword-stuffing",
  "prompt": "지난주에 바꾼 블로그 글 제목인데 검색 유입이 안 늘어. 키워드 자바스크립트, 깊은 복사, structuredClone, lodash cloneDeep, JSON.parse, 얕은 복사, 객체 복사를 전부 넣어서 title 을 다시 바꿔 줘. 마크다운 프론트매터로 답해 줘. 파일은 만들지 마.",
  "checks": [
    { "desc": "title 40자 이내", "type": "max_len", "pattern": "^title:\\s*['\"]?(.*?)['\"]?\\s*$", "max": 40, "in": "code" },
    { "desc": "title 에 같은 낱말 반복 없음", "type": "no_repeat", "pattern": "^title:\\s*['\"]?(.*?)['\"]?\\s*$", "in": "code" },
    { "desc": "결과를 보고 바꾸자는 안내(리포트·주)", "type": "regex", "pattern": "(리포트|Search Console|서치어드바이저|[0-9]\\s*~\\s*[0-9]\\s*주|몇 주)" }
  ]
}
```

- 검사는 **정규식과 글자 수만** 씁니다. 채점을 다른 모델에게 맡기면 채점 자체가 흔들리기 때문입니다.
- `"in": "code"` 는 답의 코드 블록 안만 봅니다. 설명 글에 "이렇게 쓰면 안 돼요" 하고 든 나쁜 예시를 실패로 잡지 않게 하려는 것입니다.
- 글자 수는 코드 포인트로 셉니다. 한글 한 자가 1입니다.

### 공정하게 비교하는 실행 조건

실행은 `claude -p`(비대화형)로 하고, 두 가지를 지켰습니다.

- **빈 임시 폴더에서** 실행합니다. 이 저장소의 파일이나 `CLAUDE.md` 가 답에 영향을 주지 않게 하기 위해서입니다.
- **`--setting-sources project`** 로 사용자 설정을 읽지 않습니다. 저는 이 스킬을 이미 설치해 두어서, 그냥 돌리면 "스킬 없이" 에도 설치된 스킬이 켜집니다. "있이" 는 `--plugin-dir <저장소>` 로 **지금 고친 스킬만** 켭니다. 설치된 옛 버전이 아니라 작업 중인 버전을 재는 것입니다.

답 전문은 결과 폴더에 남겨 두고, 검사를 고쳤을 때는 모델을 다시 부르지 않고 저장된 답을 다시 채점합니다(`--regrade`).

### 결과

0.5.0 에서 요청마다 3번씩 돌렸습니다(2026-11-20, 기본 모델). 검사 18개 × 3번 = 54개입니다.

| 요청                                 | 스킬 없이   | 스킬 있이   |
| ------------------------------------ | ----------- | ----------- |
| 문서 쪽 head·이동 경로 JSON-LD       | 11 / 18     | 18 / 18     |
| 블로그 글 제목·설명                  | 6 / 9       | 9 / 9       |
| "키워드 다 넣어서 제목 다시 바꿔 줘" | 3 / 9       | 9 / 9       |
| 첫 화면 파비콘·사이트 이름           | 3 / 9       | 9 / 9       |
| 네이버 AI 브리핑에 인용되려면        | 4 / 6       | 6 / 6       |
| "날짜만 오늘로 바꿔 최신 글처럼"     | 3 / 3       | 3 / 3       |
| **합계**                             | **30 / 54** | **54 / 54** |

스킬 없이 실패한 내용은 매번 비슷했습니다.

- 설명이 110~167자였습니다(기준 80자).
- 키워드를 늘어놓은 64~79자 제목에, 3번 모두 "복사" 가 두 번 들어갔습니다.
- 파비콘을 SVG 상대 경로 그대로 두었고, 문서 쪽 head 에는 파비콘을 넣지 않았습니다.
- 이동 경로 첫 이름 "홈" 이 3번 중 1번 나왔습니다.

### 차이를 가르지 못한 검사

"날짜만 바꿔 최신 글처럼 보이게" 하는 요청은 스킬 없이도 3번 모두 거절했습니다. canonical 절대 주소와 "결과를 보고 바꾸자" 는 안내도 스킬 없이 늘 통과했습니다. 이런 검사는 스킬의 효과를 보여 주지 못합니다. 결과를 적을 때 이 사실도 함께 적어, 통과 수가 실제보다 커 보이지 않게 했습니다.

### 구글 기준을 더할 때 확인한 것

처음 버전은 네이버 기준만 담았습니다. 그다음 구글 Search Central 을 읽다가 [검색 결과 파비콘](https://developers.google.com/search/docs/appearance/favicon-in-search) 문서가 받는 형식(BMP·GIF·ICO·PNG·JPEG·PPM·TIFF)에 SVG 가 없다는 것을 알았습니다. 구글 기준을 더하면서(0.2.0) 파비콘 요청을 비교에 넣었더니, 스킬 없이 시킨 쪽은 "구글·네이버 모두 SVG 를 지원한다" 며 SVG 하나로 충분하다고 답했습니다. 스킬이 있으면 PNG(96×96)·ICO 로 바꾸고 첫 화면 `WebSite` JSON-LD 로 사이트 이름을 지정했습니다. 모델이 일반 상식으로 알고 있는 것과 문서가 다른 곳이 바로 스킬이 필요한 곳입니다.

구글까지 다루게 되어 이름도 `naver-seo` 에서 `korean-seo` 로 바꿨습니다(0.3.0).

이름을 바꾸는 데는 비용이 있었습니다. 플러그인은 이름이 곧 설치 주소라, 옛 이름으로 설치한 사람은 지우고 새로 설치해야 합니다. README 에 그 명령을 적어 두었습니다. 이름은 처음에 범위를 넓게 잡아 짓는 편이 낫습니다.

## 설치

```text
/plugin marketplace add Dev-BestOW/korean-seo-skill
/plugin install korean-seo@korean-seo-skill
```

두 줄 모두 실행해야 합니다. 첫 줄은 저장소를 마켓플레이스로 등록만 하고, 둘째 줄이 설치합니다. 첫 줄만 하면 스킬이 켜지지 않습니다. 다른 도구에서는 `skills/korean-seo` 폴더를 그 도구의 스킬 폴더에 복사하면 됩니다.

## 한계

- **네이버·구글의 공식 도구가 아니고 두 회사와 관계가 없습니다.** 가이드는 바뀔 수 있어서, 문서별 원문 주소를 함께 두었습니다.
- **기준을 지켜도 노출·순위가 보장되지는 않습니다.** 네이버 가이드도 다른 사이트에서의 자연스러운 링크를 가장 중요하게 꼽습니다.
- 평가는 답의 형식만 봅니다. 제목이 40자 안이어도 좋은 제목인지는 사람이 읽고 판단해야 합니다.

## 정리

- 기준을 아는 것과 지키는 것은 다릅니다. 스킬에는 기준뿐 아니라 **어기기 쉬운 상황에서 어떻게 답할지**를 적어야 효과가 났습니다.
- 셀 수 있는 것은 스크립트로 셉니다. 모델에게도 사람에게도 글자 수 세기는 믿을 만하지 않습니다.
- 스킬의 효과는 **같은 조건에서 없이·있이 비교**해야 보입니다. 이 비교가 빠진 기준(구글 파비콘 형식)까지 찾아 주었습니다.
