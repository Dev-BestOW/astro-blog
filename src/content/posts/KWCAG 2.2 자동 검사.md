웹 접근성 인증을 앞둔 프로젝트에서는 컴포넌트마다 "이건 왜 접근성을 지킨다고 할 수 있나요?" 에 답할 근거를 모읍니다. 저는 React 디자인 시스템 BestOW UI 를 만들면서 그 근거를 **문서 대신 CI 가 매번 확인하는 테스트**로 남기기로 했습니다. 이 글은 그렇게 해 보니 자동 검사로 무엇이 지켜지고, 무엇은 끝까지 사람이 봐야 했는지에 대한 기록입니다.

## 33개 항목을 먼저 나눴습니다

KWCAG 2.2(KS X OT0003:2022)는 4원칙 14지침 33개 검사항목입니다. 디자인 시스템이 책임질 수 있는 범위부터 나눴습니다.

| 구분 | 항목 수 | 예 |
|---|---:|---|
| 라이브러리가 지원 | 18 | 키보드 사용 보장, 초점 이동과 표시, 레이블 제공, 텍스트 명도 대비 |
| 일부 지원 (쓰는 쪽과 나눠 책임) | 9 | 대체 텍스트(아이콘 이름은 지원, 이미지 내용은 쓰는 쪽) |
| 쓰는 쪽 몫 | 2 | 기본 언어 표시, 찾기 쉬운 도움 정보 |
| 해당 없음 | 4 | 자막 제공, 자동 재생 금지 등 |

항목마다 "해 둔 것 / 쓰는 쪽이 할 일 / 확인 방법" 세 칸을 채운 표를 Storybook 에 공개했습니다. 핵심은 세 번째 칸입니다. "확인 방법" 이 사람의 기억이 아니라 테스트 이름이어야 다음 변경에서도 지켜집니다.

## 1단계: 모든 스토리를 실제 브라우저에서, 두 테마로 axe

Storybook 의 Vitest 애드온으로 모든 스토리(약 260개)를 실제 브라우저에서 렌더링하고 axe 를 돌립니다. 같은 스토리를 **라이트·다크 두 테마로 한 번씩** 돌리는 것이 중요했습니다. 다크 모드의 대비 문제는 라이트만 검사하면 영원히 안 보입니다. 같은 검사를 Chromium·WebKit·Firefox 에서 돌립니다.

열어야 보이는 상태(Select 목록, 대화상자)는 axe 가 못 봅니다. 그래서 `play` 함수로 목록을 열어 둔 스토리를 따로 만들어 열린 상태까지 검사합니다.

이 단계가 실제로 잡은 것:
- 라이트 모드 보조 글자색 대비 3.32:1, 다크 모드 버튼 hover 글자 대비 3.3~4.38:1
- 달력 날짜 버튼 이름 "2026년 10월 15일 …" 에 화면에 보이는 "15" 가 낱말로 없음(KWCAG 6.5.3 레이블과 네임) → 이름을 "15, 2026년 10월 목요일" 처럼 보이는 숫자로 시작

## 2단계: axe 가 못 보는 것은 E2E 로

axe 는 DOM 을 정적으로 봅니다. 화면을 바꿔야 드러나는 문제는 Playwright E2E 로 확인합니다.

- **고대비 모드(forced-colors)**: Windows 고대비에서는 배경색과 그림자가 지워집니다. 켜진 Switch 가 통째로 사라지고, 선택된 탭·현재 페이지·진행 막대가 보이지 않았습니다. 시스템 색(Highlight)으로 다시 그리고, E2E 가 "배경이 시스템 강조색인지" 확인합니다. "투명이 아닌지" 만 보면 안 됩니다. 버튼은 고대비에서 브라우저가 ButtonFace 로 칠해서 상태 표시가 없어도 통과해 버립니다.
- **320px 리플로·글자 간격·기본 글꼴 2배**: 320px 에서 인증번호 6칸이 화면보다 넓어 가로 스크롤이 생겼고, 글자 크기가 px 라 브라우저 기본 글꼴을 키워도 커지지 않았습니다. 글자 크기를 rem 으로 바꾸고 E2E 로 고정했습니다.
- **키보드 시나리오**: 대화상자 포커스 가두기와 닫은 뒤 포커스 복귀, 메뉴 화살표 이동. trigger 없이 연 Modal 을 닫으면 포커스가 페이지 처음으로 사라지는 문제를 여기서 찾았습니다.

## 3단계: 테스트가 너무 쉽게 통과하면 의심합니다

접근성 테스트는 "통과" 가 아무 의미 없을 때가 많습니다. 테스트가 그 상황을 만들지 못하면 구현이 틀려도 통과하기 때문입니다. 그래서 핵심 테스트는 **구현을 일부러 망가뜨려서 실패하는지** 확인합니다. 예를 들어 Switch 를 직접 구현할 때 "form reset 에 처음 값으로 돌아간다", "required 면 꺼져 있는 동안 검증에 실패한다" 등 여섯 군데를 하나씩 지워 보고, 매번 테스트가 실패하는지 봤습니다.

## 4단계: 자동 검사의 끝 — 스크린리더는 직접 들어야 합니다

모든 자동 검사를 통과한 뒤 VoiceOver(macOS + Safari)로 체크리스트 13개 항목을 직접 들었습니다. 여기서 네 건이 나왔습니다.

- Combobox "결과가 없어요" 안내가 읽히지 않음
- NumberInput 이 "선택 항목 대치됨, 2" 로만 읽힘(단위 없음)
- FileUpload 삭제 알림이 다음 버튼으로 옮긴 포커스에 묻힘
- 삭제 버튼에서 Tab 으로는 파일 크기를 들을 수 없음

배운 것은 두 가지입니다. live region(알림 영역)은 **처음부터 DOM 에 있어야** 하고, 글자를 담은 채 새로 생기면 무시됩니다. 그리고 **입력·포커스 이동과 같은 순간에 바꾸면** VoiceOver 가 버립니다. 그래서 입력이 멈춘 뒤 0.8초, 포커스를 옮긴 뒤 0.5초 있다가 알림을 넣습니다. 이 타이밍 문제는 axe 로도 E2E 로도 잡을 수 없었습니다.

## 정리

| 확인 방법 | 잡은 것 |
|---|---|
| 스토리 axe (라이트·다크, 3개 브라우저) | 대비, 이름·레이블, 역할 |
| E2E (Playwright) | 고대비, 리플로·글꼴 크기, 키보드·포커스 이동 |
| 변이 확인 | "통과하지만 아무것도 안 지키는" 테스트 |
| 스크린리더 직접 점검 | 알림 타이밍, 읽히는 문장의 자연스러움 |

자동 검사는 "다시 깨지지 않게" 지켜 주는 데 강합니다. 처음 발견은 여전히 사람이 직접 써 보고 들어 봐야 했습니다. 다만 한 번 찾은 문제를 테스트로 남겨 두면, 그 뒤로는 사람이 다시 들을 필요가 없습니다.
